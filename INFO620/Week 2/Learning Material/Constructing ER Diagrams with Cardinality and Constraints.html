Constructing ER Diagrams with Cardinality and Constraints

Enterprise-level databases require precise representation of how entities interact. The ER diagram formalizes these interactions using graphical symbols, crow’s foot notation, and integrity constraints.

Cardinality Types

Cardinality defines the number of entity instances that may participate in a relationship. The three primary cardinalities are as follows:

  1. One-to-One (1:1)
    Example: Each building has one facilities manager.
  2. One-to-Many (1:N)
    Example: One customer can place many orders.
  3. Many-to-Many (M:N)
    Example: Students enroll in multiple courses, and courses have multiple students.

Relational databases require M:N relationships to be decomposed into two 1:N relationships using a bridge (or associative) entity.

Participation (Optionality)

Participation determines whether an entity’s involvement in a relationship is mandatory or optional. For example:

  • A department must have a manager (mandatory).
  • An employee may have a parking space (optional).

Participation rules ensure accurate system constraints and prevent invalid data states.

Keys in ER Models

Keys serve as identifiers within the model, as follows:

  • Primary keys uniquely identify entity instances.
  • Foreign keys enforce referential integrity in later relational schemas.
  • Candidate keys provide alternative identification options.

These concepts directly support normalization, which you will learn about in Week 4.

Applied Example

A retail business scenario might include the following:

  • Customer (CustomerID PK)
  • Order (OrderID PK, CustomerID FK)
  • Product (ProductID PK)
  • OrderLine (OrderID FK, ProductID FK, Quantity)

This example demonstrates resolving M:N relationships via OrderLine.
