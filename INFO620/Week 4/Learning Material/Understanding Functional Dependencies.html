Functional dependencies (FDs) form the mathematical basis of normalization. They describe relationships between attributes within a relation and reveal how data elements depend on one another.

According to Khurana (2024), a functional dependency X → Y means that for any two tuples in a relation, if they share the same value of X, then they must share the same value of Y. Here, X determines Y.

Determinants and Dependents

A determinant is the attribute (or set of attributes) on the left side of a dependency, while the dependent attribute is the one determined by it. For example:

  • StudentID → StudentName
    StudentID is the determinant; StudentName is dependent.

Types of Functional Dependencies

There are multiple types of functional dependencies:

  1. Full functional dependency
    Y is fully functionally dependent on X if removing any attribute from X invalidates the dependency.
  2. Partial dependency
    Occurs when an attribute is dependent on only part of a composite key.
    Example:
    (OrderID, ProductID) → ProductName
    If ProductName depends solely on ProductID, then the dependency is partial.
  3. Transitive dependency
    Occurs when X determines Y and Y determines Z, so X indirectly determines Z.
    Example:
    EmployeeID → DepartmentID
    DepartmentID → Manager
    Therefore, EmployeeID → Manager

These dependency types indicate whether a relational design is prone to anomalies.

Identifying FDs from Business Rules

Consider the following rule:
“A professor teaches one course each term, but a course may have multiple professors across terms.”

From this, you can determine the following:

ProfessorID → CourseID (for a given term)
(CourseID, Term) → ProfessorID

This step of interpreting business rules into dependencies is essential for real database design.
