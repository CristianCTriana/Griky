Star Schemas, Snowflake Schemas, and Advanced Dimensional Concepts

Dimensional models can be designed using different schema types depending on business needs, data volume, and normalization preferences.

A star schema organizes the data warehouse as one central fact table connected to multiple denormalized dimension tables.

Advantages

  • Simplest and fastest schema
  • Optimal for business intelligence (BI) tools (Tableau, Power BI)
  • Reduced number of joins → faster query performance

Example

FactSales(FactKey, ProductKey, CustomerKey, StoreKey, DateKey, Revenue)

Surrounded by dimensions: Product, Customer, Store, Date

A snowflake schema normalizes dimension tables into multiple related tables.

Advantages:

  • Reduces redundancy
  • Better data integrity

Disadvantages:

  • More joins, leading to slower queries
  • More complex for business users

Example

Product → ProductCategory → ProductDepartment

Slowly Changing Dimensions (SCDs)

Dimensions often need to store historical changes, such as when a product changes categories.

There are three types of SCDs:

  • Type 1: Overwrite old data
  • Type 2: Add new row to track history
  • Type 3: Add new columns for limited history

Type 2 is the most common in analytical environments.

Grain and Fact Table Design

The grain defines the level of detail stored in the fact table. For example:

One row per sales transaction One row per product per day One row per website session

Choosing the correct grain is essential for accurate analytics.

Case Example: Retail Data Warehouse

A retail chain might track the following:

  • SalesFact: Revenue, units sold, discount
  • Dimensions: Product, Customer, Time, Promotion, Region

This structure supports rich reporting on trends, segmentation, and store performance.
