Semana 3
Protocolos de Red, Puertos y el Modelo OSI

 

Welcome back to ISSC640. This is Week 3, and the topic is Network Protocols, Ports, and the OSI Model. In Week 2, you learned to think in terms of network scale: LAN, MAN, and WAN, and you practiced tracing the path that data follows from a user to a destination. Week 3 gives you another powerful tool: layered troubleshooting. When you combine path thinking with layered thinking, you can diagnose problems faster and communicate more clearly.   

Let us start with a common support ticket: “The website is not working.” That sentence is a symptom, not a diagnosis. The website might not work because the device has no connection, because the device has no valid IP address, because DNS cannot resolve names, because routing is failing, because a firewall blocks the destination port, or because the web service is down. Those are very different causes, and they require different fixes.  

Week 3 introduces three connected ideas that help you reduce that uncertainty. The first is protocols, which define how communication happens. The second is ports, which help devices direct traffic to the correct service. The third is the OSI model, which is a way to organize communication into layers so you can test where the failure occurs.  

Among your Week 3 goals, you will focus on three concepts. First, you will understand what protocols and ports do. Second, you will understand the OSI model and how it maps to real networking. Third, you will practice using the OSI model as a checklist that starts with basic connectivity and moves upward toward application services.  

By the end of this week, you should be able to take a vague symptom and turn it into a structured investigation plan.  

Let us begin with protocols. A protocol is a set of rules that systems follow so they can communicate reliably. Protocols define how data is packaged, how connections are established, how errors are handled, and how messages are interpreted. Without protocols, devices could not agree on what a message means.  

In networking, you will see protocols at many layers. Some protocols handle addressing and routing. Some handle reliable delivery. Some support application services like web browsing, email, and name resolution. The important point for Week 3 is that protocols exist because communication requires coordination. Devices must agree on how to speak.  

Now let us talk about ports. A port is a logical number used to identify a service on a host. Think of an IP address as the street address of a building. A port is the specific door inside that building. A single server can run multiple services, such as a web service and an email service, because each service listens on different ports. When a client sends traffic to a server, the destination port tells the server which application should receive the traffic.  

Ports matter because many network controls are built around them. Firewalls often allow or block traffic based on port numbers. If a user can reach the internet but cannot reach a specific service, it might be because the necessary port is blocked. This is common in restrictive environments like hotels, guest networks, or public Wi-Fi.  

Now, the OSI model. The OSI model is a conceptual framework that divides communication into layers. You can think of it as a map of responsibilities. Each layer handles a specific part of communication. The reason this model is valuable is that it gives you a structured way to troubleshoot. If a higher layer depends on a lower layer, and the lower layer is broken, then the higher layer cannot work no matter what you do at the application level.  

The OSI model is often presented as seven layers. You do not need to memorize every detail at once, but you do need to understand the flow.  

  • Layer 1 is the physical layer: cables, signals, wireless radio, and the basic ability to transmit bits.  

  • Layer 2 is the data link layer: local network communication, switching behavior, and how devices share a local segment.  

  • Layer 3 is the network layer: IP addressing and routing between networks.  

  • Layer 4 is the transport layer: delivery mechanisms and ports used by applications.  

  • Layers 5 through 7 cover session, presentation, and application: how applications establish conversations, format data, and provide services.  

Many network professionals combine layers 5 through 7 into “the application layer” for practical troubleshooting. The key is that the OSI model is not a rigid rule. It is a way to organize thinking.  

Now let us make this practical with a scenario: a user cannot load a website.  

If you apply the OSI model, you start at the bottom.  

At layers 1 and 2, you ask: is the device connected. If wired, is the cable connected and is the link light active. If wireless, is the device connected to the correct Wi-Fi network with a stable signal. Can the device reach the local gateway.  

At layer 3, you ask: does the device have a valid IP address. Does it have the correct gateway. Can it reach a known external IP address. If routing is broken, DNS and web browsing will fail.  

At the name resolution step, which sits between layers 3 and 7 depending on how you think about it, you ask: can the device resolve the website name to an IP address. If DNS fails, users often say “the internet is down,” even though the network might be fine.  

At layer 4, you ask: can the device reach the destination on the required port. Web traffic typically uses specific ports for web services. If the port is blocked, you might reach some sites and not others, especially if security settings differ.  

At the application layer, you ask: is the web service responding. Is the site down. Is the user blocked by authentication issues. Is there a certificate problem. Is the application returning errors.  

Now notice what this checklist does. It prevents you from guessing. If the device has no valid IP address, there is no reason to worry about ports. If DNS cannot resolve, there is no reason to reinstall the browser. If port access is blocked, changing the website settings on the user device will not help.  

This is why the OSI model is so useful. It organizes evidence collection. It also gives you language to communicate. You can say, “The issue is at the network layer because the device cannot reach the gateway,” or “The issue is at the transport layer because the destination port is blocked,” or “The issue is at the application layer because the service is down.”  

Now let us connect this to protocols and ports again. Protocols define how each layer behaves. Ports are part of transport layer behavior and application service identification. When you understand these pieces, you can interpret common symptoms more accurately.  

For example, if a user can browse many websites but cannot reach a secure internal site, you might suspect a port filtering rule, a firewall policy, or a service outage. If a VPN works on home Wi-Fi but not on a hotel network, you might suspect port and protocol restrictions. If email sends but does not receive, you might suspect different service ports or server-side issues, and you would use a layered checklist to confirm what is working and what is not.  

Another important idea is that symptoms can appear at a higher layer while the cause is at a lower layer. A user might say, “The email app is broken,” but the device might simply be on the wrong Wi-Fi network. Or the device might have a valid IP address but wrong DNS settings. Or the firewall might block a required port. Your job is to locate the cause, not to accept the first label.  

Week 3 also improves your ability to document and escalate. If you open a ticket with an internet provider, the provider will ask for evidence. They will want timestamps, loss measurements, and reachability tests. If you can say, “We have stable LAN connectivity but cannot establish transport-layer connections to this destination port,” you are providing actionable information. If you can say, “DNS resolution is failing from this network, but IP reachability is intact,” you are narrowing the problem.  

This week is also a reminder that troubleshooting is a process, not a set of tricks. A strong process scales across scenarios. It works for web issues, email issues, VPN issues, and application performance issues. The OSI model gives you that process.  

In Week 4, you will build on these skills by learning about network media and connectivity. That week focuses on the physical and link layers, including cables, wireless media, and connection methods that influence speed and reliability. You will see how the lower layers you referenced in Week 3 have real-world constraints that shape everything above them.
