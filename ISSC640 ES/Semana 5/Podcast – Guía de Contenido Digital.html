Dispositivos de Red e Interconexión

 

Welcome back to ISSC640. This is Week 5, and the topic is Network Devices and Internetworking. In Week 4, you looked at network media and connectivity and learned that physical and wireless conditions shape everything above them. Week 5 adds the next layer of foundation: the devices that make networks work. When you understand what each device does, you can diagnose problems faster and you can explain network behavior with clarity.  

A network is not one thing. It is a system of components that work together: access points, switches, routers, and security devices. Each component has a job. Each job is linked to a specific type of decision. When something fails, your goal is to find which decision is failing.  

During Week 5, you will focus in three concepts. First, you will learn the roles of common network devices and what problems each one solves. Second, you will understand internetworking, which is how separate networks are connected so traffic can move across boundaries. Third, you will practice a troubleshooting mindset that maps symptoms to device roles, so you can focus on the correct component instead of guessing.  

By the end of Week 5, you should be able to explain the difference between switching and routing, describe how wireless access integrates into a LAN, and identify why boundary devices are common sources of widespread outages.  

Let us begin with the idea of a device as a role. A device name is less important than the function. If you memorize device terms without understanding what they do, troubleshooting will feel like guesswork. If you understand roles, troubleshooting becomes a set of logical tests.  

A wireless access point provides wireless connectivity to a local network. It connects wireless clients to the LAN, translating radio communication into wired network access. The access point is usually not responsible for routing traffic to the internet, but it is responsible for whether wireless clients can connect reliably and whether they can reach the LAN. That is why a common symptom pattern is: wired devices work, wireless devices do not. When you see that pattern, you focus on wireless conditions and the access point role.  

A switch connects devices within a local network segment. Switches forward traffic inside a LAN based on local addressing. In practical terms, a switch enables many devices to communicate on the same local network. If a switch fails, you often see local connectivity failures: devices cannot reach each other, or a large set of devices in one area loses access. Switch issues can be caused by hardware failure, power loss, misconfiguration, or physical link problems, which you learned about in Week 4.  

A router connects different networks. A router decides where to send traffic next when the destination is not on the local network. This is the core of internetworking. If you want to reach an external site, a different subnet, or a cloud service, you need routing. This is why a common symptom pattern is: internal access works, but external access fails. When internal works, your LAN switching is likely functional. When external fails, your routing or boundary configuration may be the problem.  

A firewall filters traffic based on security rules. Firewalls often sit at boundaries, controlling what enters and leaves a network. Firewalls can block traffic by destination, by port, by protocol, or by other conditions. Because firewalls can be very specific, they often create selective failures. For example, web browsing might work, but one application fails because a specific port is blocked. When you see selective failure, you consider filtering rules, ports, and the service requirements from Week 3.  

Now, internetworking. Internetworking is the process of connecting multiple networks so they function together. Inside a building, you have local switching and wireless access. When traffic needs to reach another network, such as the internet or another office, it crosses a boundary device, usually a router or firewall. That boundary device uses routing rules and security policies to determine whether traffic can pass and where it should go.  

Think of internetworking as a path. A user device sends traffic to the local network. The local network forwards it to a boundary device. The boundary device forwards it to an upstream network, often a provider. Eventually, the traffic reaches the destination service. The return traffic follows a similar path in reverse. If any device on that path makes the wrong decision, communication fails.  

Now let us connect this to troubleshooting. Troubleshooting in Week 5 is often about identifying the boundary.  

If a user cannot access anything at all, you start with connectivity and media, as Week 4 taught you. If the user can access the LAN but not the internet, you suspect the boundary device. If only wireless fails, you suspect wireless access. If only one application fails, you suspect a port or firewall rule. These symptom patterns are clues. They are not proofs, but they guide your first tests.  

Let us take the scenario: internal file shares work, but no external websites load. What does that mean. It suggests that local connectivity is intact. The switch is likely forwarding local traffic. The wireless access point might be working if wireless clients can still access internal resources. That points to the boundary device. The boundary device might have a missing default route, a down upstream interface, a DNS forwarding problem, or a firewall policy issue that blocks outbound traffic.  

A missing default route is a classic example. If a router does not know where to send traffic that is not local, it cannot forward it. So even with stable links, the internet appears “down.” This is why configuration control and monitoring matter. A small change can have a large impact.  

Now consider another scenario: wireless users cannot connect or cannot get stable access, but wired devices are fine. That points to access points, wireless interference, and wireless configuration. In that case, changing router settings would not be a smart first step. You would start with wireless checks: is the access point online, is the SSID present, is authentication working, is there congestion, and is signal coverage adequate.  

Now consider a selective scenario: web browsing works, but a specific application fails. That often points to filtering, ports, or service-side issues. You might look at firewall rule changes, port reachability, and application requirements. This connects back to the ports and OSI model from Week 3.  

Week 5 also emphasizes that network devices make forwarding decisions. Switches forward based on local addressing. Routers forward based on IP routing rules. Firewalls filter based on policies. Access points mediate wireless access. When you see a failure, ask: which decision is failing. That question transforms troubleshooting from guesswork into analysis.  

Now, a practical note: many organizations combine functions in modern devices. A single device can be a router and a firewall. A wireless router in a home might combine switching, routing, wireless access, and security filtering. That does not change the core roles. It simply means you must think about which function is involved.  

Week 5 is also a reminder about documentation and change management. Many widespread outages are not mysterious. They are caused by configuration changes. If you change firewall rules, you can break an application. If you change routing, you can break external access. If you change switch configurations, you can isolate users. Strong teams manage this with backups, approval processes, and the ability to roll back quickly.  

Finally, Week 5 connects directly to Week 6, which will focus on internetworking in more detail through IPv4 and IPv6 addressing. Routing depends on addressing. If addressing is incorrect or inconsistent, device decisions will fail. So Week 5 gives you the device roles, and Week 6 gives you the addressing logic that devices use to connect networks.  

So the Week 5 takeaway is this: device roles define responsibilities, and responsibilities guide troubleshooting. When you map the device path and identify the boundary, you often find the issue faster.  

Let us close with reflection questions. Consider completing the following optional activity.   

Choose a common activity, such as opening a cloud document. List the devices involved from the user to the service: access point or wired connection, switch, router, firewall, provider link, and destination service.  

Now, for each device, write one failure that could occur. For example, an access point could have congestion, a switch port could have errors, a router could have a missing default route, and a firewall could block a required port.  

Finally, consider a symptom pattern: internal works but external fails. Which device role would you investigate first, and what would you check? 

If you can answer those questions, you are thinking in Week 5 terms: device roles, internetwork paths, and boundary-focused troubleshooting.
