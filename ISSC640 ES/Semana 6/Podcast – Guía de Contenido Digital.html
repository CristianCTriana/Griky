Interconexión de redes (Parte 2: Direccionamiento IPv4 e IPv6)

 

Welcome back to ISSC640. This is Week 6, and the topic is Internetworking Part 2: IPv4 and IPv6 Addressing. In Week 5, you learned about network devices and internetworking and how routers and boundary devices connect networks. Week 6 explains the logic those devices use to make forwarding decisions. That logic is built on addressing. If addressing is wrong, routing fails, even when cables, Wi-Fi, and devices are working.  

If you have ever seen a device that “connects” but cannot reach what it needs, you have seen why Week 6 matters. A device can connect to Wi-Fi, show signal bars, and even communicate locally, but still fail to reach resources on other networks. Many of those issues come down to three settings: the IP address, the subnet mask or prefix, and the default gateway.  

You will focus on three concepts this week that will help you achieve your Week 6 goals. First, you will understand what an IP address does and how it supports routing. Second, you will understand subnetting at a practical level, meaning how networks are divided and how devices decide what is local. Third, you will compare IPv4 and IPv6 at a high level and understand why IPv6 exists and how transition often works in real environments.  

By the end of Week 6, you should be able to look at an IP configuration and quickly identify common misconfigurations, such as a wrong gateway, a subnet mismatch, or an address conflict.  

Let us begin with the role of IP addressing. An IP address identifies a device on a network and also tells routers where that device belongs. Addressing supports two essential tasks: local delivery and routed delivery.  

Local delivery is when the destination is on the same network segment. Routed delivery is when the destination is on a different network. A device must decide which it is. That decision depends on the subnet information.  

This is where the idea of a network portion and a host portion becomes important. The network portion identifies the network. The host portion identifies the individual device within that network. The subnet mask, in IPv4, or the prefix length, in IPv6, is what defines how much of the address is network and how much is host.  

Now let us talk about the default gateway. The default gateway is the router address that a device uses when the destination is not local. If a device wants to reach something outside its subnet, it sends traffic to the gateway. If the gateway is wrong or unreachable, the device will often be able to talk locally but not remotely. That symptom pattern appears constantly in support tickets.  

Let us make this concrete. Imagine a laptop on a local network. It can reach the printer and a nearby desktop. That suggests the laptop is on the right Wi-Fi and the local switch and access point are functioning. Now the laptop tries to reach a cloud service and fails. That suggests the failure is in routed delivery. The first checks are: does the laptop have a valid IP address, does it have the correct subnet mask or prefix, and does it have the correct default gateway? 

If the gateway points to an address that is not on the same subnet, the laptop cannot reach it. If the subnet mask is wrong, the laptop might misclassify destinations as local when they are not, or remote when they are local. If the IP address conflicts with another device, communication can be intermittent and confusing.  

Now let us briefly compare IPv4 and IPv6.  

IPv4 uses a dotted decimal format and has a limited address space. That limitation is one of the reasons networks often use private addressing and translation techniques. IPv4 also uses subnet masks to define the network portion. In practice, many end devices receive IPv4 settings through automatic configuration services. When those services are misconfigured, large groups of devices can be affected quickly.  

IPv6 uses a longer hexadecimal format with a much larger address space. The purpose of IPv6 is to support continued growth and to reduce the pressure created by limited addresses. IPv6 uses prefix lengths to define the network portion. Many organizations operate in a transition mode for a long time. This is often called dual-stack, where both IPv4 and IPv6 operate at the same time.  

Dual-stack is practical because not every service supports IPv6 in the same way, and not every environment migrates at the same pace. The important point is that IPv4 and IPv6 can coexist, and troubleshooting sometimes requires you to understand which protocol a device is using to reach a destination.  

Now, you do not need to become an addressing expert in one week. But you do need to learn how to recognize common failure patterns.  

Here are a few of the most common addressing problems you will see.  

Wrong default gateway. This is the classic. The device has an IP address and can communicate locally, but cannot reach remote networks. The fix is to correct the gateway setting. If many devices are affected, you check the configuration service that provides addresses.  

Subnet mismatch. The device might have a subnet mask that does not match the network design. This can cause the device to believe certain destinations are local when they are not, or remote when they are local. It can also create confusion when devices that should be on the same subnet cannot communicate consistently. 

Duplicate IP address conflict. Two devices using the same IP address can create intermittent failures, because traffic may go to the wrong device depending on timing. Symptoms can appear random. Address conflicts can occur when static addressing is used incorrectly or when devices are misconfigured.  

DNS misconfiguration. DNS is not addressing itself, but it is often grouped with addressing triage because it determines whether names can resolve to addresses. A device might have valid IP settings, but if DNS is wrong, users will experience failures that feel like the internet is down.  

Now, why does Week 6 matter for internetworking? Because routers depend on addressing to forward traffic. Routers maintain routing tables that tell them how to reach different networks. End devices use their own subnet and gateway settings to decide when to route. If either side is wrong, communication fails.  

Week 6 also matters for troubleshooting communication boundaries. In Week 5, you learned that when internal works and external fails, you often check boundary devices. Week 6 adds a step: confirm whether the device is even sending traffic to the boundary device correctly. If the gateway is wrong, you can reboot routers all day and the client will still fail.  

Now, let us talk about a practical workflow you can use in support.  

When a device cannot reach remote services, run an addressing triage.  

First, check IP address, subnet mask or prefix, and default gateway. Confirm they match the network you expect. If the device is using automatic configuration, release and renew the settings and see if the values correct themselves.  

Second, check basic reachability. Can the device reach the default gateway? If it cannot, you may have a local link issue or wrong gateway. If it can, try reaching a known external IP address. If that works, but names do not work, the issue may be DNS.  

Third, compare with a working device on the same network. If one device works and another does not, compare their addressing side-by-side. Differences often reveal the root cause.  

This workflow is simple, but it is powerful. It also helps you communicate. You can say, “The client has a correct IP but the gateway is wrong,” or “The client has a subnet mismatch,” or “The client can reach the gateway and an external IP but cannot resolve names, suggesting DNS.” 

Week 6 also prepares you for more advanced networking work. Address planning, subnetting strategies, and IPv6 transition require structured thinking. For now, the goal is to build practical competence: understand what the fields mean and recognize the common failure patterns.  

In Week 7, you will shift to cloud services. Cloud networking depends heavily on correct addressing, routing, and name resolution. Cloud services also introduce new patterns of access and dependency. The addressing skills you learn in Week 6 will help you interpret cloud connectivity issues with more confidence.  

So the Week 6 takeaway is this: if you want to troubleshoot routing, start with addressing. Address, subnet, and gateway are foundational. When they are correct, many other problems become easier to isolate. When they are wrong, nothing else matters.
