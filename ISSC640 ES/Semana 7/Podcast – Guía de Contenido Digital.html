Semana 7
Servicios en la Nube

 

Welcome back to ISSC640. This is Week 7, and the topic is Cloud Services. In Week 6, you focused on IP addressing and learned that addressing and gateways determine whether traffic can be routed. Week 7 brings all the pieces together. Cloud services sit outside your local network, which means access depends on the entire path: local connectivity, boundary devices, WAN performance, DNS, and identity systems.  

 

Cloud services are now central to modern work. Email, file storage, collaboration, identity systems, and many business applications are delivered from cloud environments. That convenience comes with a key operational reality: your users are now highly dependent on external services and the network path that reaches them.  

To help you achieve your Week 7 goals, we will focus on three concepts this week. First, you will understand what cloud services are, at a practical level, and how organizations use them. Second, you will understand the shared responsibility idea, meaning what the provider handles and what your organization still must handle. Third, you will practice troubleshooting cloud issues by separating the path into three categories: local environment, provider connectivity, and service-side availability.  

By the end of Week 7, you should be able to hear “the cloud is down” and respond with a structured plan: what to test, what evidence to collect, and how to communicate findings clearly.  

Let us start with what cloud services mean in practical terms. A cloud service is a resource delivered over a network rather than hosted locally. That resource might be an application, storage, identity, or infrastructure. The cloud is not one place. It is a set of distributed systems managed by providers.  

Common cloud service categories include hosted applications, cloud storage, identity services, and infrastructure resources. Many organizations use cloud email, cloud file sharing, cloud collaboration tools, and cloud-hosted business applications. Some also use cloud infrastructure to run servers and platforms.  

Now, here is the key Week 7 idea: cloud adoption shifts responsibility rather than removing it. The provider manages parts of the service infrastructure, but your organization still manages the ability to reach the service and the ability to authenticate and authorize users. If your internet link is saturated, users will blame the cloud. If your DNS fails, users will blame the cloud. If your identity system is misconfigured, users will blame the cloud. If a firewall blocks a required port, users will blame the cloud. This is why support teams need an end-to-end troubleshooting approach.  

A useful way to think about cloud access is a simple path. A user device connects through Wi-Fi or wired LAN. Traffic passes through switches and reaches a boundary device such as a router or firewall. It then crosses an ISP or WAN link. It then reaches the cloud provider network. Finally, it reaches the service itself. Along the way, name resolution and identity services often play a central role. 

Now let us talk about the dependencies you should always consider.  

First is local connectivity, which includes wired media, wireless conditions, and basic access to the local gateway. If the local connection is unstable, cloud services will appear unstable.  

Second is boundary devices, such as routers and firewalls. These devices route traffic outward and apply filtering policies. Misconfiguration here can block specific services or all external access.  

Third is WAN performance and ISP connectivity. Cloud services depend on internet performance. Bandwidth saturation, high latency, jitter, and packet loss can degrade cloud applications, especially real-time services like video.  

Fourth is DNS and identity. DNS is required to translate service names into destination addresses. Identity is required for authentication and authorization. A cloud email service might be fully operational, but if DNS fails or authentication fails, users cannot access it.  

Now, the most practical skill in Week 7 is separating the problem into categories. When users say “the cloud is down,” you ask: is it local, is it transit, or is it service? 

A quick way to test this is comparison. If users on a different network can access the service, then the service is likely available, and the issue is local or transit. If users everywhere cannot access the service, and the provider status indicates issues, then it might be service-side. If only one site has issues, suspect the WAN link, local DNS, or boundary devices at that site.  

Let us walk through a realistic scenario. Suppose cloud email is unavailable on the corporate network. Users see authentication prompts, or the login page does not load. A few users on a hotspot can access email. That tells you a lot. It suggests the cloud service is reachable and the user accounts can authenticate, at least from another network. So now you focus on the corporate path.  

You might test DNS resolution for the service domain on the corporate network. If DNS fails or resolves incorrectly, clients will not reach the correct service endpoints. If DNS is correct, you might test whether the firewall blocks required connections. If filtering is correct, you might test WAN reachability. If WAN is healthy, you might test identity integration and authentication paths.  

Notice the pattern. You are not guessing. You are isolating dependencies.  

Now consider another scenario. A cloud file service feels slow during peak hours, and the branch office reports the worst experience. That suggests a bandwidth and congestion issue at the branch. In Week 2, you learned that WAN links can saturate. In Week 6, you learned that addressing and gateways must be correct. In Week 7, you combine those ideas. Cloud performance differs by site because the path differs by site. The fix might be a WAN upgrade, traffic prioritization, or scheduling changes, not a change to the cloud service itself.  

Now consider a selective failure scenario. One cloud application fails after a firewall policy update, but other cloud apps still work. That is a clue. It suggests that the firewall change blocked a specific destination, protocol, or port needed by that application. In that case, blaming the cloud provider will waste time. Your best move is to examine what changed and test reachability to the service endpoints.  

Week 7 also emphasizes communication. During cloud incidents, leaders often want a fast answer. Your job is to provide a clear explanation that respects the shared responsibility reality. You can say, “The cloud provider appears available, but internal DNS resolution is failing,” or “The branch WAN link is saturated during peak hours,” or “A firewall policy is blocking the required service port.” Those statements are specific and actionable.  

Cloud services also require monitoring strategies. Because services are external, you need monitoring that reflects the end-to-end path. That can include connectivity checks, DNS resolution checks for critical domains, authentication health checks, and WAN performance monitoring. The goal is early detection and faster isolation. If you can detect that DNS resolution is failing before tickets flood in, you can reduce downtime and user frustration.  

Finally, Week 7 prepares you for Week 8, which focuses on network administration and support. Cloud services change support work because you must manage vendor relationships, escalate effectively, document dependencies, and coordinate communication during outages. Week 8 will take the technical skills you built and connect them to operational practice: monitoring, ticket handling, documentation, escalation, and user support.  

So the Week 7 takeaway is this: cloud services increase dependency on the network path and on identity and DNS. Troubleshooting cloud issues requires separating local, transit, and service causes. When you map the path and test dependencies, you can diagnose faster and communicate more responsibly.  

Let us close with  an optional activity.  

Pick one cloud service, such as email or file storage. Draw the path from the user to the service. Label at least four dependencies: local Wi-Fi or LAN, boundary device, ISP or WAN link, and DNS or identity.  

Now, choose one dependency and write a quick test you would use. For example, test DNS resolution for the service domain, test reachability to the gateway, or compare access from another network.  

Finally, write one sentence you would use to brief leadership during an incident, separating what you know from what you are still testing.  

If you can answer those questions, you have the Week 7 skill: cloud troubleshooting as end-to-end path analysis, not guesswork.
